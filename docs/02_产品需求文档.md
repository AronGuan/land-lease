## 一、项目定位与成功标准

### 1.1 业务背景
某县土地主管部门以租赁方式有偿出让国有土地，**仅县城所在镇就有 3,000 余份存量合同且以纸质为主**。合同、宗地、不动产登记、历年缴费分散在档案柜、表格与各系统中，导致四类问题：

1. 合同到期与租金欠缴靠人工翻查，发现不及时
2. 产权人不知每年应缴额，往往到过户/赠与时才补缴，欠缴多年
3. 租金按年期分段计租、标准随基准地价调整，人工核算易错
4. 税务部门所需信息靠人工整理报送

**一句话目标**：把「扫描件 → 准确台账 → 催缴 → 报税」这条链跑通，**可落地交付，不是 demo**。

### 1.2 评分权重（决定投入优先级）

| 评审项 | 分值 | 关键动作 |
|---|---|---|
| **现场补档** | **40** | 陌生材料 20 分钟内入库；支持撤回重导；用对话窗口临时处理 **0 分** |
| 部署与运行 | 25 | 装得上、跑得稳、模型可现场切换、权限/日志/备份/出错处理 |
| 流程与测算 | 20 | SOP 可交给本地人员；3,000 份人天**以实测为依据**；错漏兜底 |
| 存疑判断 | 15 | 待确认清单找全、理由成立、明确要向主管部门确认什么 |

### 1.3 成功标准
- 练习集 score.py ≥ 90 分（合同要素 30 / 归集 15 / 核算 30 / 问题清单 20 / 催缴 5）
- 现场补档 20 分钟内完成「领材料 → 入库 → 展示 → 撤回重导」全链路
- 交付物齐备：可部署系统 + SOP 与测算 + 待确认清单 + 部署运维说明 + 操作手册 + 可重复测试

## 三、需求范围

### 3.1 一期建设内容（8 项）

| # | 需求 | 要点 |
|---|---|---|
| 1 | 存量合同治理 | 扫描件 OCR/VLM 识别 → 要素抽取 → 与登记/缴费交叉比对 → 问题清单 → 人工核验入库 |
| 2 | 一宗一档电子台账 | 宗地、承租人、合同、核算、缴费互相关联；按区域/状态/欠缴查询 |
| 3 | 租金核算 | **规则程序计算（AI 不参与）**；分段计租；规则可配置；过程留痕；复核后生效 |
| 4 | 到期与欠缴提醒 | 按到期时间与欠缴情况分级提醒经办人，体验接近日历 |
| 5 | 催缴通知 | 制式模板生成通知书 → 确认 → 短信通知产权人 → 跟踪缴纳结果 → 欠缴台账 |
| 6 | 合同生成与续期变更 | 按模板生成新签/续期合同，记录变更与终止并归档（**双轨并行：纸质+电子**） |
| 7 | 税务推送单 | 按税务所需字段定期生成，留存每次推送 |
| 8 | 统计查询 | 欠缴、到期、收缴率统计，支持导出 |

### 3.2 明确不做（范围红线）

- ❌ 系统接口对接：不动产登记、税务数据走**文件导出/导入**
- ❌ 在线缴费：沿用现有渠道，系统只记录并跟踪结果
- ❌ 国有土地出让/划拨管理、公有住房租金管理
- ❌ 全面电子化：坚持**双轨平行**（纸质留档 + 电子台账）

### 3.3 交付成果（6 项）

1. 可部署系统（源码 + 离线部署包，干净服务器可装）
2. 合同治理作业流程 SOP 与测算（每步 AI 做什么、人核对什么、出错如何处理；3,000 份人天以实测为据）
3. 评测集处理结果与待确认清单（现场调阅）
4. 部署与运维说明（服务器配置、模型方案与实测、安装步骤、日常运维）
5. 经办人员操作手册（覆盖导入、复核、催缴、推送、查询）
6. 可重复运行的测试（至少能用练习集验证识别与核算结果）

## 四、核心业务流程（端到端 SOP）

### 4.1 主链路 8 步（人机分工）

| 步 | 执行者 | 动作 |
|---|---|---|
| 0 准备 | 人（一次性） | 导入计租标准/街路级别、不动产登记导出、缴费记录、减免登记 |
| 1 上传 | **人** | 新建批次，拖入扫描件/拍照件（文件名「档案号_页序.jpg」） |
| 2 存盘归组 | 系统 | 写磁盘 `storage/{批次}/{档案号}/{页序}.jpg` + SHA256；同档案号多页合成一份文件 |
| 3 AI 抽取 | 系统 | VLM 逐页抽取 → 多页合并 → 每字段置信度 → 规则预校验（证件校验位、电话 11 位、日期合法性） |
| 4 三级判定 | 系统 | L1 直接识别 / L2 反推（写链路） / L3 留空记问题 |
| 5 归宗比对 | 系统 | 旧地号↔单元号映射 → 多合同归宗 → 与登记/缴费比对 → 生成 13 类问题清单 |
| 6 复核 | **人** | 批量确认（~76%）+ 逐项核对改字段（~24%） |
| 7 核算 | 系统 | 规则引擎：分段计租 → 月度折算 → 减免 → 实缴归集 → 欠缴 + 留痕 |
| 8 入库 | 系统 | 生成/更新一宗一档台账 → 提醒 → 催缴 → 税务推送 |

### 4.2 增量回路
新合同 / 续期 / 变更 / 现场补档 → 新批次 → 识别 → 归宗 → **重算该宗应缴与欠缴** → 更新台账、问题清单、催缴对象（不重跑全量）。

### 4.3 现场补档 20 分钟预算

| 环节 | 预算 |
|---|---|
| 领材料 + 上传 | 2 分钟 |
| 识别 + 归宗 + 重算 | 3 分钟 |
| 人工复核（批量确认 + 逐份） | 8–10 分钟 |
| 更新台账/清单/催缴对象 + 展示 | 3 分钟 |
| 评委指定一份撤回并重导 | 3–5 分钟 |

## 六、识别与数据治理策略

### 6.1 三级识别（核心设计）

| 级别 | 触发 | 系统行为 | 处理方式 |
|---|---|---|---|
| L1 直接识别 | 置信度高 + 规则校验通过 | 直接填值 | **自动通过** |
| L2 反推 | 看不清但可由其他数据推出 | 填值 + **记录反推链路** | **人工复核** |
| L3 不可识别 | 看不清且推不出 | 留空 + 记问题清单 | **人工录入** |

**强制降级的四种情形**：字段有涂改、与登记/缴费冲突、关键字段低置信、进入存疑待确认。
*实测教训*：LX-001 年租金真值 3,998.25，VLM 首次识别给出 **4,018.25（恰为涂改前内容）**——涂改件必须送复核。

### 6.2 反推规则库

| 规则 | 推导式 |
|---|---|
| 金额互推 | 年租金 = 计租标准 × 面积（查四套标准表） |
| 日期互推 | 终止日 = 起始日 + 租赁年限 |
| 宗内互证 | 同宗地续期/前合同要素承接 |
| 缴费反推 | 缴费记录金额佐证合同年租金 |
| 跨源比对 | 登记面积 ↔ 合同面积（不一致则记问题） |
| 格式校验 | 证件校验位、电话位数、日期区间 |

落库格式：`{字段, 证据（原图位置）, 推导规则[], 结果, 置信度}`（JSON 存 `field_extraction.reason`）。

### 6.3 归宗打分模型（实测样例 LX-027/028/048）

| 证据 | 分值 |
|---|---|
| A 原合同编号指针命中 | +60 |
| B 宗地号/单元号位段换算一致 | +30 |
| C 承租人证件号一致 | +15 |
| D 面积一致 | +10 |
| E 坐落归一化一致 | +10 |
| F 起租日 = 前份终止日 +1 天（校验） | +10 |

≥40 分归同一宗；<40 分新开宗地并记「登记数据中无对应宗地」；冲突降级人工复核。

**旧地号↔单元号映射**（口径第十条）：`09-05-0106` ↔ 单元号 `000000009005GB00106F00089385` 第 7–9 位(009) / 10–12 位(005) / 15–19 位(00106)，前导零可省略。

### 6.4 问题清单 13 类（严格使用，不得自创）

文件层：关键字段有涂改、合同缺页、缺宗地图、年租金大小写不一致、证件号码异常、联系电话缺失或无效、坐落或宗地号与登记不一致、面积与登记不一致
宗地层：合同到期未续、承租人已变更未办合同变更、登记数据中无对应宗地、缴费记录异常
通用：**存疑待确认**（涉及两份合同填签订较晚的一份）

### 6.5 存疑处理（口径第十二条）
按现有资料**不能确定**怎么算的 → 列出各种说得通的算法 → **按应缴最少（对产权人有利）暂算** → 列入问题清单（写明存疑之处、暂按算法、与最高算法差额）→ 待主管部门书面确认后重算。

## 七、租金核算规则要点

| 条款 | 规则 |
|---|---|
| 三 | 自然年度计收，6/30 前缴纳；起租/终止当月均计入；年度应缴 = 适用年租金 × 计费月数 ÷ 12 |
| 四(一) | 固定方式按合同约定；大小写不一致**暂按大写**并记问题 |
| 四(二) | 随标准调整：面积 × 当年 1 月 1 日有效标准，四舍五入到分 |
| 四(三) | 面积与登记不一致，**暂按合同面积**并记问题 |
| 四(四) | 涂改有签章按涂改后；无签章按第十二条存疑 |
| 五 | 续期自原合同期满次日起；期满未续按最后合同计收至基准日；解除/收回计至当月 |
| 六 | 减免：先算当年应缴 ×（1 − 减免比例） |
| 七 | 实缴归集：重复票据计一次；按日期票据序；注明年度归该年（超额为多缴不冲抵）；未注明冲抵最早欠缴年 |
| 八 | 欠缴 = 各年度应缴和 − 实缴和（含多缴），不计滞纳金，负数为多缴 |
| 九 | 催缴对象取登记现权利人，查不到取最新承租人；电话优先登记 |
| 十 | 旧地号 ↔ 单元号位段映射 |
| 十二 | 存疑按应缴最少算法暂算 |

**计算纪律**：金额一律 `DECIMAL(14,2)` + Python `Decimal`，禁用 float；评分容差 **±0.01 元**；每次核算落 `rent_calc_trace`（输入快照 + 公式 + 口径版本）。

## 八、人机分工与「处理方式」

### 8.1 定义（易被误解，务必明确）
- **自动通过** = 系统有把握，经办人**批量确认**（每份几秒，看摘要不逐项对照原件）——**不是跳过人工**
- **人工复核** = 逐项对照原件核对，可改可退回

### 8.2 为什么不全量复核
3,000 份全复核 ≈ 26 人天，等于回到人工时代；而「76% 批量确认 + 24% 逐项复核 ≈ 2 人 5.5 天」正是流程与测算 20 分要的答案。评分规则（自动通过且对 +1 / 错 **−1** / 复核 +0.5）本身就是防乱放的兜底。

### 8.3 批量确认交互（必须二次确认）
点「批量确认 38 份」→ 弹窗展示：
1. 统计摘要（份数/涉及宗地/最低与平均置信度/涂改冲突存疑 0 份/校验通过率）
2. **最低置信度 Top3 预警清单**（具体档案号、字段、AI 值 vs 登记值）
3. **抽检比例**（默认 10% 自动转复核队列）
4. 确认后逐份写审计日志，**5 分钟内可整体撤销**

### 8.4 复核工作台交互
- 左原件、右字段；**所有字段可改**（不只是 L3 字段）
- 任一字段被改 → 记 `field_correction`（改前/改后/人/时间）+ 审计日志 + 该份自动降为「人工复核」
- 三个出口：确认入库 / 退回问题清单 / 标记存疑待确认

## 九、数据模型（24 张表）

分层与关键表见 `docs/01_数据模型设计.md`，DDL 见 `docs/schema.sql`：

```
接入层   import_batch · file_object
合同层   contract_doc · field_extraction · field_correction
宗地层   parcel · parcel_doc · registry_parcel · registry_street_level
规则层   rent_standard · reduction_record
核算层   rent_due · rent_calc_trace
缴费层   payment_record · payment_alloc
问题层   issue
催缴层   collection_notice · sms_task · payment_track
税务层   tax_push · tax_push_item
支撑层   sys_user · audit_log · model_config · model_call_log · config_item · backup_record
```

**设计六原则**：批次为骨架 ｜ 字段级可追溯 ｜ 计算与证据分离 ｜ 原件不入库（磁盘 + 元数据 + SHA256）｜ 结果可导出（列名对齐标准答案 CSV）｜ 只增不改（审计 append-only）。

**评分对齐**：`process_type` 由关键字段全对的置信度阈值决定（阈值可配置）；租金额外 `rent_calc_trace` 保证可解释；issue 类型严格 13 项。

**按宗地整体切分**（非按文件随机）：同一宗多份合同必须同侧，否则测试宗地缺成员、标准答案的欠缴金额无法比对。
