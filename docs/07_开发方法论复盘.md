# 我是怎么开发这个项目的

> 国有土地租赁智能管理系统 · 单人 + AI，3 天，从读题到可离线部署
> 整理自 2026-10-27 ~ 10-29 的真实开发日志（含每次决策、每个 bug 的根因）

---

## 总纲一句话

**我没有"写代码"，我做的是四件事：先把评分表变成目标函数，再把不确定性变成可测量的数字，然后用标准答案当尺子反复量，最后把每个 AI 会出错的地方设计成看得见的东西。**

代码是这四件事的副产品。

## 二、十条核心思路

### 1. 先读评分表，再读需求

**做法**：拿到题先找"分值表"，不是找"功能清单"。

**本项目证据**：读题当天写下的第一句结论是"评分权重 = 现场补档 40 / 部署运行 25 / 流程测算 20 / 存疑判断 15"，然后才做模块规划。第 3 天补的部署包、SOP 与测算，都是为了这两项 45 分——它们不是"顺手加的文档"，是**一开始就排进计划的交付物**。

**为什么有效**：功能清单告诉你"能做什么"，分值表告诉你"必须做成什么"。前者无限，后者有限。在有限时间里，只做后者。

---

### 2. 决策前置，一次锁死，允许推翻但只在开工前

**做法**：把所有不可逆的选择提前一次性定完，写进文档；开工后不改架构。

**本项目证据**：开工前锁了 5 项——技术栈、数据库、识别通道、模块分层、存储方式。其中**技术栈是推翻重来的**：最初定 Go，我改成 Python（因为核算逻辑要频繁改、要能跑数据核对脚本，Python 迭代快）。改的时间点是"还没写一行业务代码"。

**为什么有效**：架构决策的成本随时间指数上升。第 1 小时改是改主意，第 1 天改是重写，第 2 天改是延期。

---

### 3. 先造尺子，再开发

**做法**：在写功能之前，先把"怎么算对"变成可执行脚本。

**本项目证据**：`verify_calc.py`（对标准答案逐条比对）、`verify_test20.py`（盲测 20%）、`smoke_api.py`（28 项接口）、`drill_check.py`（9 项一键预检）。整个项目每一次改动，都以这些脚本的输出为准，不以"我觉得对了"为准。

**为什么有效**：这是整个项目最值钱的一条。有了尺子，"进度"从感觉变成数字：今天 26/30，明天 30/30。没有尺子，就只能靠"差不多了"判断，而"差不多了"是所有交付事故的起点。

**你可以怎么用**：任何有标准答案的项目（对账、报表、算法题、迁移），第一件事是写一个能输出"X/Y 对"的脚本，而不是先写功能。

---

### 4. 误差必须归因到机制，不接受"差不多"

**做法**：任何不一致，先问"为什么差"，不问"怎么补"。

**本项目证据**：核算从 26/30 到 30/30，三个差异的根因分别是：
1. 「零捌分」解析取错字符 → 改为按「角/分」标记字定位
2. 同一宗地两份合同期间重叠 → 引入截断规则（旧合同自新合同起始日前终止）
3. 残余 **0.01–0.07 元**漂移 → 反推出标准答案生成器用的是 **float64 链式 + Python round(x,2)**，于是把自己的实现改成同一条计算链，全绿

第 3 条最能说明问题：**0.01 元的差异，我花了时间去反推对方怎么算的**，而不是加个容差糊过去。因为"差 0.01"在一年 618 条记录上会变成"差几块钱"，在对账场景等于错。

**为什么有效**：容差是掩盖，归因是消灭。前者会在规模化时爆炸。

---

### 5. 实测优先于调研（但先调研，再实测）

**做法**：调研决定"候选集"，实测决定"用哪个"。实测成本通常只要十几分钟。

**本项目证据**：调研显示 OmniDocBench 前四名都是 1.5B 以下的专用小模型（MinerU2.5 / GLM-OCR / PaddleOCR-VL），全面压过通用大模型。但实测发现：
- 我手上的 API Key 是 Coding Plan 型，开源版 `qwen3-vl-32b/8b/235b` **全部 404 model_not_found**
- `vanchin/deepseek-ocr` 在模型列表里，但调用报 **400 product not activated**
- 真正能用的只有三个闭源视觉模型

**结论**：调研说"开源模型更好"，实测说"你的 Key 用不了开源模型"。如果只信调研，会在实现到一半时才发现路不通。

还有一个更值钱的实测：LX-001 首读给出的年租金是 **4018.25**，而真值是 **3998.25**——4018.25 恰好是**涂改前**的内容。这一次实测直接决定了整个产品的核心设计（见第 6 条）。

---

### 6. 把 AI 的不确定性设计成界面，而不是藏在准确率里

**做法**：不报"准确率 97%"，而是让每个字段自己说"我有多可靠"。

**本项目证据**：三级识别 + 四类强制降级：
- 🟢 L1 直接识别 → 可批量确认
- 🟡 L2 反推（金额从大写推、终止日从起租日+年限推）→ 必须对照原件
- 🔴 L3 不可识别 → 必须手工录入

四类**整份强制转人工**：有涂改 / 与登记冲突 / 关键字段低置信（<0.90）/ 关键字段不可识别。
批量确认时弹窗强制显示**最低置信度 Top3**。

**为什么有效**：准确率是一个"事后统计"，经办人无法在当下使用它；而"这个字段是黄的"是"当下可操作的信息"。**把模型的不确定性翻译成使用者的动作**，AI 才敢真正交给业务人员。

---

### 7. 可逆与可追溯是架构约束，不是事后补日志

**做法**：任何写操作都设计对称的反操作；任何数字都能追到输入。

**本项目证据**：
- 撤回批次 → 整批回滚 + 级联重算，实测**完全对称**：确认 27 宗 / 411,849.31 → 撤回 26 宗 / 403,377.79 → 再确认 27 宗
- 问题清单：确认入库时自动置 `resolved`（留痕不删除），撤回时反向 `reopen`
- 每次核算落 `rent_calc_trace`（输入快照 + 公式 + 口径版本）
- 每次改字段落 `field_correction` + `audit_log`（前后值 + 操作人 + 时间）

**为什么有效**：现场演示时，评委可以随时点"撤回"，我敢让他点，因为我知道数字会一模一样地回来。**可逆性是可演示性的前提。**

---

### 8. 表象 → 根因句 → 小改动（不重构）

**做法**：每次修 bug，先写一句"根因：……"，再动代码；能小改不大改。

**本项目证据**：这类循环走了十几轮，每轮都留下根因句：
- "存量合同 50 份对不上" → 根因：**前端硬编码字面量**，与数据库漂移 → 改为后端实时汇总
- "详情点了没反应" → 根因：`render: () => <Button>` **无 onClick**
- "导出只有 10 条" → 根因：导出用的是**当前页 rows** 而非全量
- "生成催缴后状态不变" → 根因：催缴状态列是**写死的 Tag**
- "到期日历没标记" → 根因：**不是 bug，是数据空态**（2026 全年仅 2 条到期）+ 月份硬编码无翻月

最后一条特别重要：**先判断是 bug 还是空态**，否则会去修一个不存在的 bug。

**为什么有效**：根因句是唯一能防止"修了 A 坏了 B"的东西。没有根因句的修复都是试错。

---

### 9. 跨页面的数字，必须能自证

**做法**：凡是同一个事实出现在两个地方，就写一条恒等式去对。

**本项目证据**：一次全量一致性检测 8 项引用完整性孤儿全 0，并验证：
```
应缴和 403,377.79 − 实缴和 294,776.86 = 108,600.93 = 台账欠缴和，差异 0.00
```
还有宗地数 = 列表条数、问题清单条数 = open + resolved、催缴对象数 = 欠缴 > 0 的宗地数。

**为什么有效**：用户第一次看到两个页面数字不一样，就会认为整个系统不可信。恒等式是最便宜的信任建设。

**附带规矩**：数字一改，全库 grep 旧值。我把"50→40、139→110、76%→100%"这类同步做过好几轮——**改数字比改代码更容易漏**。

---

### 10. 实测与推断必须分开写

**做法**：文档里明确标注"这是实测"还是"这是推算，待校准"。

**本项目证据**：
- 部署包做完后写的是"**未做运行验证**（按要求只出包与说明）"
- SOP 测算里，机时（6.44 s/页）和比例（66.7% 自动通过）标"实测"，人工复核 4 min/份 标"**待计时演练校准**"，并给出 3/4/5/6 分钟四档敏感性
- 文末单列一节「如实说明（我们自己看到的不足）」，写了 4 项

**为什么有效**：把推断说成实测，第一个追问就崩。分开写，反而显得可靠——**因为可校验**。

## 三、十个决策点复盘

| # | 决策点 | 选项 | 我的选择 | 放弃的理由 |
|---|---|---|---|---|
| 1 | 技术栈 | Go / **Python** | Python | 核算规则要反复改、要写核对脚本，Python 迭代快；Go 编译检查在这场景是负担 |
| 2 | 数据库 | SQLite / **MySQL** | MySQL | 部署环境是政务服务器，MySQL 是标配；金额用 DECIMAL 不走浮点 |
| 3 | 识别通道 | 单通道 / **双通道+可切换** | 双通道 | 赛题明确要求"模型可配置可切换"，这是 25 分里的一个动作 |
| 4 | 租金谁算 | 让模型算 / **规则引擎算** | 规则引擎 | 赛题硬约束：租金必须规则程序计算，AI 只做抽取 |
| 5 | 识别分级 | 一刀切准确率 / **三级 + 强制降级** | 三级 | 一刀切无法指导经办人"这一份要不要逐项看" |
| 6 | 原件存储 | 存数据库 / **本地磁盘 + 元数据入表** | 磁盘 | 图片进 DB 会让备份和查询都变重 |
| 7 | 问题清单类型 | 自由扩展 / **严格 13 类** | 严格 13 类 | 自创类型 = 三个月后没人能统计；为此加了映射 + 断言 |
| 8 | 前端与原型关系 | 重新设计 / **对齐原型** | 对齐原型 | 原型已定视觉与信息架构，重做是浪费；只补关键缺失 |
| 9 | 表格任务 | 同步执行 / **提交即返回 + 后台跑** | 异步 | 84 页要 12 分钟，同步会把请求挂死，且刷新就看不见状态 |
| 10 | 部署形态 | nginx + Node + 后端三件套 / **后端托管静态** | 单端口 | 目标机只装 Python + MySQL，"少一个组件就少一类故障" |

## 四、我是怎么指挥 AI 干活的

这部分可能比代码更有参考价值——**同一套工具，指令方式不同，产出差一个量级。**

| # | 做法 | 具体表现 | 效果 |
|---|---|---|---|
| 1 | **先给约束，不给步骤** | 给评分表、口径文件、标准答案、样本目录，不说"你该怎么写" | AI 自己会去找关键约束，比喂步骤更准 |
| 2 | **自己拍板，不让 AI 拍板** | 技术栈 Go→Python、开源通道用硅基流动、加"基础数据"第 7 组导航——都是我定的 | 决策权留着，AI 负责把选项摆清楚 |
| 3 | **用截图说话** | 界面问题一律截图 + 红框标注 | 一句话省掉三轮来回描述 |
| 4 | **只要根因，不要"已修复"** | 每轮追问"为什么会这样" | 逼出的是机制级修正，不是症状级补丁 |
| 5 | **不让 AI 自证** | 明确要求"改完不要用浏览器验证，我自己看" | 省掉大量无效截图流程，我用自己的眼睛验收 |
| 6 | **禁止大改，只许小改** | "对齐原型时只补关键缺失点，不做大重构" | 3 天做完 16 页没有一次推倒重来 |
| 7 | **数字不对就追到底** | "存量合同应为 41"、"为什么问题清单和类型页对不上" | 逼出的是口径问题，不是显示问题 |
| 8 | **要求实测，不接受"应该没问题"** | 每个功能都要"实测（LX-0xx）：…"的记录 | 3 天里没有一次交付是"看起来能用" |

**一条体会**：AI 最容易犯的错不是写错代码，是**悄悄简化需求**——把"原件对照"简化成"字段列表"、把"全量导出"做成"当前页导出"、把"撤回级联重算"做成"改个状态"。我的做法是**每次都拿原型/原始需求逐项对照**，发现被简化就退回去。

## 五、踩过的坑，换来的规矩

| 坑 | 根因 | 换来的规矩 |
|---|---|---|
| VLM 把涂改件读成涂改前金额（4018.25 vs 3998.25） | 模型看到的是划掉的字 | **涂改一律强制人工复核**，不许自动通过 |
| VLM 输出「□固定 ☑随基准地价调整」「商服用地」 | 直接写库与标准表不匹配，走错核算分支 | 识别后必须**归一化再校验**，原文保留在 `ai_value`，归一化值存 `final_value` |
| 金额差 0.01 | 对方生成器是 float64 链式 + round | 舍入链路要**反推对方实现**，不是加容差 |
| 字段名被当成问题类型（"承租人类型"） | 直接把字段名塞进 issue_type | **13 类是封闭集合**，映射 + 断言校验 |
| 可选字段为空被记"不可识别" | 没区分必填/选填 | 定义 `OPTIONAL_FIELDS`，空值不产生问题 |
| OCR 把 `××镇` 读成 `xx镇` → 判定坐落不一致 | 脱敏符归一化漏了大小写 | 6 条误报中 4 条是假阳性，**归一化要比对前做完** |
| 土地级别为空 → 全部退化为固定租金（应缴 4421.52 算成 2804.39） | 级别只在宗地台账/街路映射里，合同不载明 | 缺值时按**街路名反查级别**，再回退宗地主档 |
| 撤回后宗地不消失 | `autoflush=False`，状态没 flush 就重算 | 重算前**必须 flush** |
| 确认 4 次生成 4 份催缴通知书 | 接口不幂等 | **重复调用必须幂等**：有则复用、无则新建 |
| 前端硬编码"50 份""97.4%" | 写死的字面量与库漂移 | 所有统计**由后端实时汇总**，前端只做派生计算 |
| 后台长任务随会话中断丢失 | 同步执行写在请求里 | **提交即返回 + 独立 Session + 逐份 commit** |

## 六、如果重做一遍，我会改三件事

**1. 第一小时就写核对脚本，而不是第三小时。**
这次是先建模型再写 `verify_calc`。虽然没出大问题，但有半天时间我是靠"看起来对"在判断。

**2. 先定"人能操作什么"，再定"系统能算多少"。**
三级识别是第 2 天才想清楚的。如果第 1 天就确定"经办人只能看到三种颜色"，前面的数据模型会少走一些弯路（比如 `reason` 反推链路的 JSON 结构会设计得更完整）。

**3. 测算参数应该边做边测，而不是最后补。**
SOP 里人工复核 4 min/份 现在还是待校准参数。如果每次人工复核都顺手记一次耗时，最后就不用"给敏感性区间"来兜底。

## 七、给别人讲的 5 分钟版本（口播提纲）

> 下面这段可以直接照着说。

**开场（30 秒）**
"这个系统做的是把三千份纸质土地租赁合同变成一本能算钱、能追责、能催缴的账。有意思的不是它有多少功能，是它怎么被做出来的——一个人，三天。"

**第一段：我先算分，不算功能（60 秒）**
"拿到题我没看功能清单，我先看分值表：现场补档 40 分，部署运行 25，流程测算 20，存疑判断 15。这四个数字就是我的项目计划。所以我第三天做的不是加功能，是打包和写测算——因为那 45 分一开始就在计划里。"

**第二段：我给自己造了一把尺子（90 秒）**
"任何对账类的活，最怕的是'差不多对了'。所以我先写核对脚本，让它告诉我 618 条应缴记录对了几条。第一天是 26 个宗地对，第二天是 30 个。中间有一次差 0.01 元，我去反推对方的计算是用浮点链式还是定点——最后发现是浮点加两位舍入。我改了自己的实现去对齐，而不是加个容差。因为差 0.01 在对账场景里等于错。"

**第三段：我让 AI 认输（90 秒）**
"我做过一次实测，模型读出来的年租金是 4018.25，真值是 3998.25。为什么？因为那份合同上年租金被划掉改过，模型读的是划掉的旧数字。这一下让我确定了整个产品的核心设计：AI 不许说自己'大概对'。每个字段必须标绿黄红三级，看不清就得说看不清；只要有涂改、有冲突、置信度低，整份合同强制转人工。我不追求'准确率 97%'这种事后数字，我要的是经办人当下知道'这一份要不要对着原件看'。"

**第四段：我敢让人当场点撤回（60 秒）**
"现场演示最怕评委说'你把这个撤回去'。我敢让他点，因为撤回会整批回滚、级联重算，数字一模一样地回来——27 宗 41 万，撤回变 26 宗 40 万，再确认又回到 27 宗。可逆，才敢演示。"

**收尾（30 秒）**
"所以这三天我做的其实不是写代码，是三件事：把评分表变成目标函数，把标准答案变成尺子，把 AI 的不确定性变成界面上的颜色。代码只是这三件事的副产品。"
